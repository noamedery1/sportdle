# ספורטדל

חידת שחקן יומית לחמישה מועדוני כדורגל ישראליים, מוגשת כקובץ HTML אחד
שעומד בפני עצמו. הכללה של **ביתרדל** שרץ בייצור.

```
npm install                 # מתקין Playwright + כרומיום
npm run scrape              # שואב את המקורות (ראה אזהרה על worldfootball)
npm run enrich              # מצליב מקורות → data/clubs/<slug>.json
npm run build               # מרכיב dist/index.html + מריץ את כל הבדיקות
npm run serve               # http://localhost:4173
```

### worldfootball — איך זה נפתר

הסקרייפר של Playwright נחסם: דפי `vs<Y>-<Y+1>/squad/` יושבים מאחורי
אתגר Cloudflare, הבקשה הראשונה עוברת וכל השאר מקבלות 403 קבוע.

**לא נעשה שום ניסיון לעקוף זיהוי בוטים.** הסקרייפר מנווט כדפדפן רגיל,
מחכה שהאתגר ייפתר מעצמו, נסוג בהדרגה, ואחרי חמישה כישלונות ברצף
עוצר נקי ומדפיס מאיפה להמשיך.

מה שכן עובד: בדפדפן שכבר עבר את האתגר, `fetch` רגיל מאותו origin
מחזיר 200 עם התוכן הנכון — בדיוק כמו לחיצה על תפריט העונות. זה מה
ש-`data/urls/<slug>-wf-console.js` עושה, עם השהיה של 1.5 שניות.
ראה [MISSING.md](MISSING.md) להוראות מלאות.

**בדיקת האימות:** worldfootball החזיר 408 שחקני בית"ר מול 410 במאגר
הייצור — בדיוק בדיקת השפיות שסעיף 7 במפרט ביקש.

עמידות: כל דף נשמר כ-HTML ב-`data/raw/html/<slug>/` לפני הפרסור,
ו-`--reparse` בונה הכול מחדש **בלי לגעת ברשת**. אפשר לאסוף לאורך
ימים או מכתובות שונות בלי לאבד כלום.

### הגישור בין אנגלית לעברית

worldfootball מחזיר שם באנגלית, כל השאר בעברית. שלושה גשרים, לפי סדר:

1. **`wikilang`** — הקישור הרשמי בין ערך עברי לערך אנגלי. מזהה מדויק
   שוויקיפדיה מתחזקת, לא ניחוש תעתיק.
2. **`enbridge`** — כשהכתיב הלטיני שונה ("Beni Tabak" מול
   "Benny Tabak"): מחפשים באנגלית והולכים משם לקישור העברי.
   מתקבל רק אם **שנת הלידה בערך זהה לזו של worldfootball**.
3. **גשר מבני** — שנת לידה + חפיפת עונות. אם בדיוק שחקן אחד בכל צד
   מתאים, זה אותו אדם. דו-משמעיות → לא משייכים.

מי שאף גשר לא תפס נשאר ברשימת התעתיק הידני ב-`data/review/`.
הוא לא נכנס למשחק ולא מקבל שם מומצא.

`enbridge` הוא השלב האיטי בצינור — חיפוש נפרד לכל שחקן, וויקיפדיה
מווסתת. לכן הוא **המשכי**: שומר ל-`data/raw/<slug>-enbridge.json`
כל עשרה חיפושים, וזוכר גם את מי שנבדק ולא נמצא. אפשר לעצור אותו
באמצע ולהריץ שוב — הוא ימשיך מאיפה שהפסיק ולא יחזור על עבודה.

### למה לא לשאוב עמדה משרת ההתאחדות

דף השחקן נותן שנת לידה ואזרחות אבל **לא עמדה**, וזה כ-2,000 טעינות
דף. worldfootball נותן את שניהם בבת אחת.

## מעבר מביתרדל בלי לאבד משתמשים

### איך זה פרוס

הכול בריפו `noamedery1/beitardle`. שני דומיינים על אותו שירות:

| כתובת | מה קורה | אחסון |
|---|---|---|
| `beitardle.up.railway.app/` | ביתרdle כרגיל, עם רצועה ל-SportDle | הרצפים הקיימים |
| `beitardle.up.railway.app/sportdle/` | SportDle — הנתונים מביתרדל **עוברים** | אותו origin |
| `sportdle.up.railway.app/` | מפנה ל-`./sportdle/` — **התחלה מאפס** | origin נפרד |

**הדומיין הקנוני הוא `sportsdel.techbynoam.com`**, והוא כתוב במקום
אחד בלבד — `siteUrl` ב-`config/site.json`. ממנו נגזרים `og:url`,
`og:image`, `rel=canonical`, קישורי השיתוף, הפוסט היומי והקליפים.

הכתובות של Railway בטבלה למעלה עוד מגישות תנועה, ולכן צריך **301
מהן לקנוני**. המקום לזה הוא Cloudflare ולא הקוד: הייצור הוא קבצים
סטטיים, ואין בו אפליקציה שתריץ middleware. חוק אחד ב-Cloudflare —
Redirect Rule על `http.host ne "sportsdel.techbynoam.com"` →
`concat("https://sportsdel.techbynoam.com", http.request.uri)`,
301 — מכסה את כל הדומיינים בלי לגעת בקוד ובלי סיכון ללופ.

`scripts/serve.mjs` מכיל את אותה הפניה בשביל שרת הפיתוח ובשביל
המקרה שהוא יוגש אי פעם, עם `CANONICAL_HOST` לדריסה. localhost
נשאר בחוץ.

זו החלטה מודעת: מי שנכנס מהכתובת החדשה מתחיל נקי, ומי שממשיך
בכתובת הישנה ממשיך כרגיל. `localStorage` הוא לפי origin ואין דרך
לגיטימית להעביר אותו בין דומיינים.

**ההפניה חייבת להישאר יחסית.** הפניה מוחלטת לדומיין השני הייתה
מאבדת בשקט את הרצף של כל שחקן — `tools/qa-deploy.mjs` מפיל את
הבנייה אם מישהו יהפוך אותה למוחלטת.

### פקדי המעבר

האייקון `⇄` לבדו היה קטן ולא מובן, אז בשני הדפים יש טקסט:

* **בדף הישן** — רצועה מתחת ללשוניות: "יש גם מכבי ת"א, הפועל ת"א,
  מכבי חיפה והפועל ב"ש — עברו ל-SportDle". 347×60 במסך 375.
* **ב-SportDle** — גלולה שמראה את המועדון הנוכחי:
  "⇄ מועדון: מכביdle · החלפה", מתעדכנת בכל החלפה.

בית"ר כאן היא **בדיוק** מה שרץ בייצור: 410 שחקנים ו-119 החידות הראשונות
זהות לאתר החי, כולל חמשת התיקונים האחרונים (`זהי אליהן` → `צחי אליחן`,
וארבע עמדות). אומת מול `beitardle.up.railway.app` בזמן אמת, לא מול העותק
המקומי.

מקור האמת הוא `reference/beitardle-versus.html` (BUILD b38). הקובץ הישן
`reference/beitardle.html` (b23) נשאר כהיסטוריה — **הלוח שלו נבדל
מהייצור מחידה #4 והלאה**, אז אסור לבנות ממנו.

### ההגירה עצמה

`migrateFromBeitardle()` ב-`src/engine.js` רצה פעם אחת בטעינה ומעבירה:

| ביתרדל | ספורטדל |
|---|---|
| `beitardle:v2:<n>` | `sportdel:beitar:p<n>` |
| `beitardle:streak` | `sportdel:beitar:streak` |
| `beitardle:stats` | `sportdel:beitar:stats` |
| `beitardle:yshown` | `sportdel:beitar:yshown` |
| `beitardle:seen` | `sportdel:seen` |

ובנוסף קובעת `sportdel:club = "beitar"`, כדי שמשתמש חוזר ינחת ישר
בביתרdle ולא במסך הבחירה. המפתחות הישנים **לא נמחקים** — אפשר לחזור אחורה.

> **⚠ זה עובד רק אם ספורטדל מוגש מאותו origin שביתרדל היה בו.**
> `localStorage` הוא לפי origin, ואין דרך לגיטימית להעביר אותו בין
> דומיינים. בכתובת חדשה הפונקציה פשוט לא מוצאת כלום ולא עושה כלום —
> לכן היא בטוחה להריץ תמיד.

נבדק: משתמש עם רצף 7, 12 משחקים וארכיון → נוחת בביתרdle עם תג הרצף
מוצג, הסטטיסטיקה במקום והארכיון זמין.

תוך כדי תוקן באג שהיה גם בייצור: `showStreak()` נקראה לפני
ש-`puzzleNo` נקבע, אז **תג הרצף לא הופיע בטעינה** אלא רק אחרי סיום
חידה. במעבר זה קריטי — משתמש חוזר היה חושב שאיבד את הרצף.

## קרב חברים

מצב רב־משתתפים בזמן אמת, בלשונית שנייה. הוכלל מ-`reference/beitardle-versus.html`.

**חדר שייך למועדון אחד.** הנתיב הוא `rooms/<slug>/<code>` — רמה אחת
עמוקה יותר מביתרדל, כדי שחמשת המועדונים לא יתנגשו זה בזה ולא בחדרים
הקיימים של ביתרדל באותו פרויקט.

### ⚠ צעד חובה לפני שזה עובד

חוקי הפיירבייס הנוכחיים מתירים `rooms/<code>` בלבד, ולכן פתיחת חדר
נכשלת ב-`PERMISSION_DENIED`. **צריך להדביק את
[`config/firebase-rules.json`](config/firebase-rules.json)** בקונסולה:
Firebase → Realtime Database → Rules.

עד שזה נעשה, המשחק לא קורס — מופיעה הודעה על המסך שמסבירה בדיוק מה חסר.

### הבריכה מסתגלת לגודל המועדון

בקרב אין משוב מצמצם, אז שחקן אלמוני הוא לא חידה קשה אלא סיבוב מת.
הסף מתחיל ב-**5 עונות**, ויורד כל עוד יש פחות מ-40 ב-CORE. **לא יורד
מתחת ל-3** — לפי המפרט זה שובר את המשחק.

| מועדון | סף שנבחר | CORE | WIDE |
|---|---|---|---|
| ביתרdle | 5 | 53 | 68 |
| באר־שבעdle | 4 | 48 | 31 |
| מכביdle | 5 | 54 | 67 |
| חיפהdle | 5 | 50 | 64 |
| הפועלdle | 5 | 41 | 54 |

רק באר־שבע יורדת ל-4 — ב-5 היו לה 31 בלבד.

### הגשר בין הסקריפטים

הקרב הוא `<script type="module">`, **ומודול לא רואה `const` שהוצהר
בסקריפט רגיל.** זה הפיל את המשחק בייצור פעם אחת. כל מה שהוא צריך עובר
במפורש דרך `window.SPORTDEL`:

```js
window.SPORTDEL = { slug, game, short, he, players, analyticsUrl, siteUrl }
```

והחלפת מועדון קוראת ל-`window.SPORTDEL.versusClubChanged(slug)`, שיוצא
מהחדר, מעדכן את הנתיב ומרענן את הבריכה.

### מה לא נבדק כאן

יצירת חדר נחסמה בחוקים, אז **הזרימה המלאה — לובי, סיבובים, ניקוד,
נוכחות — לא נבדקה מקצה לקצה.** מה שכן נבדק: המודול נטען, פיירבייס
מתחבר, הכשלון מדווח על המסך, החלפת מועדון מנתקת. אחרי עדכון החוקים
צריך לעבור על רשימת הבדיקות בסעיף 7 של מפרט הקרב — **בשני מכשירים**.

שתי הרשימות המאומתות משוחזרות במדויק, וכל חמש הספירות תואמות.

המזהים של בית"ר (3595) והפועל ב"ש (2171) שיצאו משם זהים למאומתים,
וזו הבדיקה שהשלושה החדשים נכונים.

תקופת המנדט מופרדת ל-`titlesPreState` ולא נספרת. המאגר מתחיל
ב-1969/70, אז זה לא משנה אף ספירה — רק שלא יופיעו שנים משנות ה-30
במסך העזרה.

## תיקונים ידניים

`config/names-<slug>.json` **גובר על כל מקור.** מפתח = `player_id`
של ההתאחדות או השם שהצינור הפיק. ערך = שם חדש, או אובייקט עם
`he` / `pos` / `nat` / `born` / `spells`.

`data/review/<slug>.json` הוא רשימת המשימות: מי בלי תכונות, מי
דו-משמעי, ואיזו כפילות לא נפתרה מעצמה.

> **אין התאמה אוטומטית לפי דמיון מחרוזות.** רק שוויון מדויק אחרי
> נרמול (מקף ← רווח, בלי גרשיים). כששני ערכי ויקיפדיה מתאימים
> לאותו שם, הצינור לא בוחר — הוא רושם ב-review ומשאיר ריק.
> "אריאל עוז" ו"אריאל הרוש" הם שני אנשים.

שינוי שם עובר גם ללוח החידות: `enrich` מעדכן את השם ב-
`config/schedule-<slug>.json` באותו מקום בסדר. בלי זה כל תיקון איות
לשחקן מהבריכה היה מפיל את `enrich` על "בלוח יש שמות שאינם במאגר".

חלק מהתיקונים האלה מגיעים מעצמם, מטופס שבסוף המשחק — שם ועמדה בלבד,
שלושה מדווחים נפרדים, ו-PR שמחכה לאישור. ראה
[AUTOMATION.md](AUTOMATION.md).

## לוח החידות

`config/schedule-<slug>.json` הוא רשימת שמות בסדר קבוע. חידה #1
היא הראשונה ברשימה.

* הלוח של בית"ר נטען מ-`reference/beitardle.html` — 119 החידות
  שכבר פורסמו נשמרות **byte-identical**, וזה נבדק.
* שחקן חדש שעומד בתנאי התשובה נוסף **בסוף בלבד**, בערבוב עם seed
  קבוע (`config/site.json` → `shuffleSeed`) כדי שהסדר לא יהיה כרונולוגי.
* שם שכבר בלוח ונפל מהבריכה מוחזר אליה בכוח, ומדווח ב-review.
* שם שבלוח ונעלם מהמאגר לגמרי **מפיל את ה-enrich**. זה מכוון:
  זו החלטה אנושית, לא משהו לתקן בשקט.

## הערות למי שממשיך

**עונה, לא שנה.** המאגר שומר שנת **סיום** עונה. שחקן שנרשם כ-2014
שיחק ב-2013/14, ואין בנתונים מידע אם הגיע בקיץ או בחלון החורף.
לכן התצוגה תמיד `13/14`. גם בבורר המועדונים.

**ספירת תארים.** תואר בשנה `t` נספר אם `a <= t <= b`. הכלל הזה
אומת מול כל 410 שחקני הייצור — 0 סטיות. שים לב ש-`countTitles`
בקובץ הייצור כתוב `y > a` — הוא באג רדום שלא מתפוצץ רק כי
`titles` תמיד מגיע כמספר מוכן מהצינור. כאן זה מתוקן.

**מפתחות אחסון.** `sportdel:<slug>:<key>`. כל מועדון הוא עולם נפרד:
לוח, רצף, סטטיסטיקה, ארכיון. הבחירה עצמה ב-`sportdel:club`.

**תווי השיתוף.** `●` `◐` `○` בלבד. אמוג'י צבעוני נשבר בוואטסאפ ווב
בווינדוס — נבדק בשטח שלוש פעמים ונכשל בכל אחת. יש בדיקת בנייה
שמוודאת שאף תו לא חורג מהמישור הבסיסי.

**קאש.** `dist/index.html` מכיל את כל הנתונים מוטמעים. הגרסה
(`config/site.json` → `build`) מוצגת בפוטר, כדי שאפשר יהיה לאבחן
משתמש עם עותק ישן במבט. הגש עם `Cache-Control: no-cache`.

**סטטיסטיקה קהילתית.** `analyticsUrl` ריק כברירת מחדל, וזה מכבה
את האיסוף לגמרי. אם מחברים Google Sheets — כל עדכון חייב להיות
עטוף ב-`LockService`, אחרת ספירה במקביל נדרסת בשקט.
